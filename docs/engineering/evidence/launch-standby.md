# Standby platform verification

## Interactive contract

Steadyfetch's measured endpoint used a bearer token and a synchronous JSON response. The response included rows, a summary, the number of delivered transcripts, charge information, notes, and a request ID. Invalid input produced a structured response with no transcript event. ReelSaid will offer the same interactive pattern for one selected video through an authenticated `POST /`. The native Apify interface handles accounts, multiple videos, schedules, and continuation. Both surfaces use the same transcript result and eligibility rules. [Observed competitor behavior](launch-market.md)

The stable Standby hostname belongs to the Actor or task. The per-run Container Web Server URL identifies one run. Apify sends its readiness request as `GET /` with the readiness header and expects a successful response before routing traffic. The server reads its port from `Actor.configuration.web_server_port`. The probe uses aiohttp's runner on the SDK's asyncio loop, with the SDK logger and no HTTP access log. It handles JSON from the request body. [Standby development](https://docs.apify.com/actors/development/programming-interface/standby) · [aiohttp server lifecycle](https://docs.aiohttp.org/en/stable/web_advanced.html)

The API distinguishes single-tenant Standby runs owned by the caller from multi-tenant pools owned by the Actor developer. The charge API accepts an Apify-injected request ID for attribution in a multi-tenant pool. The Python SDK charge helper in version 4.2.1 takes an idempotency key. The Python API client's run charge method also takes the request ID. These paths require separate live verification because the gateway authenticates requests before forwarding them. [Standby configuration](https://docs.apify.com/api/v2/actor-put) · [Charge events API](https://docs.apify.com/api/v2/post-charge-run) · [Actor whitepaper](https://github.com/apify/actor-whitepaper#multi-tenant-standby-mode)

Apify documents platform usage as separate from event charges in Standby. Measure zero-event platform usage and the billing account from the real deployment before committing the customer promise for Standby. The product's final event prices remain a separate release decision. [Standby billing](https://docs.apify.com/actors/running/standby#billing) · [Pay-per-event platform usage](https://docs.apify.com/actors/monetize/pay-per-event#pass-platform-usage-costs-on-to-users)

## Multi-tenant and cross-account results

Steadyfetch's Actor metadata identifies its Standby mode as `MULTI_TENANT`. The isolated ReelSaid probe used the same mode. The gateway replaced the forged caller identity and request ID on the stable URL. The first probe found that the direct run URL would forward all three forged gateway-like headers. The edge rejected a direct request that substituted the stable hostname in `Host` with HTTP 404. A forwarded-host header left the actual direct host intact. The protected build checks the SDK's stable gateway hostname and requires the caller identity, request ID, and caller-type headers before accepting a POST. The same direct attempt then returned 403. A repeat in the first account reused its existing result without another event.

The second account's zero-event request and zero-budget request incurred no event. Apify returned HTTP 400 for the test charge without a request ID. ## Production interface verification

The implementation uses the native transcript pipeline for interactive requests. Its HTTP validation rejects empty input and refers profiles, collections, and multi-video Carousels to the native run interface before any transcription. Results include inline UTF-8 SRT and WebVTT content. The request budget reserves the largest applicable tier quote before ASR. Event receipts use the request's authenticated platform attribution. A tiered rate that is unavailable in the gateway context leaves the exact USD amount empty in the immediate response.

The local contract passed readiness, invalid input, caller isolation, admission, settlement replay, sanitized logging, and OpenAPI response checks. The trusted GitHub runner started both the ordinary and Standby entry points using the Apify CLI and processed the real spoken fixture. The scheduled workflow was pinned to that verified revision and passed an on-demand run. The first private Apify build exposed an SDK environment alias difference for the Actor identifier. The regression verifies cloud startup reads it from SDK configuration. [Trusted runner verification](https://github.com/aimansour/reelsaid/actions/runs/42635450583) · [Scheduled workflow verification](https://github.com/aimansour/reelsaid/actions/runs/42635828045)

Steadyfetch returned one charged transcript event in both cross-interface directions for the same caller. A Reel previously purchased on Standby incurred a new event through the native API. A different Reel previously purchased through the native API incurred a new event on Standby. Both comparisons used the same account and explicit Reel identities. [Cross-interface comparison](https://github.com/aimansour/reelsaid/actions/runs/42636029119)

Exact private build `0.1.30` passed both Apify surfaces. The stable endpoint returned 401 without authorization and 200 for authenticated health. Empty input, an unknown field, and a profile request returned structured 400 responses. The spoken fixture returned a complete timed transcript and both subtitle formats. Its repeated request returned the cached transcript. A forged request to the per-run address returned 403. The same build also delivered the native dataset and subtitle files. The Actor remained private and its native default selection stayed unchanged. [Private Apify runtime verification](https://github.com/aimansour/reelsaid/actions/runs/42636519142)
